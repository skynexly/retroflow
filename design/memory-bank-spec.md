# 溯流计划 · 记忆系统架构设计规范 (Memory Bank Design Spec)

> 状态：草案评审通过 / UI 研发阶段  
> 责任模块：数据归档（`MEMORY BANK // 记忆库` · 桌面 02 号 Bento 卡片）  
> 核心原则：客观事件精简、多线正史指针解耦、高危角色在场可见性、零 Emoji、100% 纯矢量 SVG。

---

## 一、双维度心智模型

溯流计划的记忆划分为两大核心维度：

```
                ┌───────────────────────────────────┐
                │        记忆系统 (MEMORY BANK)      │
                └───────────────┬───────────────────┘
                                │
        ┌───────────────────────┴───────────────────────┐
        ▼                                               ▼
┌───────────────────────────────┐               ┌───────────────────────────────┐
│     副本记忆 / 事件记忆 (一期)  │               │        角色记忆 (二期)        │
├───────────────────────────────┤               ├───────────────────────────────┤
│ · 以副本世界线为发生容器      │               │ · 以具体角色为主观心智容器    │
│ · 客观描述事实因果            │               │ · 包含好感度、主观评价、心结  │
│ · 依附于存档分支 (Run)        │               │ · 跨副本沉淀与演化            │
└───────────────────────────────┘               └───────────────────────────────┘
```

> **阶段策略**：一期聚焦于**副本事件记忆**的 UI 呈现、数据结构与正史流转；二期推进**角色主观记忆**与自动提炼 Prompt。

## 二、事件记忆核心字段规范

每一条事件记忆（Event Memory）必须客观记录该片段的前因后果，严禁发散抒情：

| 字段名 | 类型 | 规范与定义 |
|---|---|---|
| `eventId` | `string` | 唯一主键，格式如 `mem_evt_{timestamp}_{random}` |
| `forkId` | `string` | 归属副本卷宗 ID |
| `forkTitle` | `string` | 副本卷宗标题（展示冗余缓存） |
| `runId` | `string` | 产生该记忆的具体存档窗口 ID（区分同副本不同线） |
| `runTitle` | `string` | 存档窗口名称/分支代号（如 `RUN-01 潜入分支`） |
| `summary` | `string` | **具体事件正文**：客观精简，清晰交代「前因 → 谁因为什么干了什么 → 最终结果如何」 |
| `keywords` | `string[]` | **事件关键词（严格 5~6 个）**：用于 RAG 检索命中与记忆激活 |
| `witnesses` | `Witness[]` | **在场角色列表**：见证并知晓该事件的角色（见下节可见性规则） |
| `source` | `'auto' \| 'manual'` | 提取来源（`auto` 结算自动提炼 / `manual` 执行员手动录入） |
| `createdAt` | `number` | 提炼生成时间戳 |
| `status` | `'candidate' \| 'canonical'` | 状态：`candidate` 候选态 / `canonical` 正史生效态 |

## 三、世界线分支与正史生效机制

在快穿无限流的设定中，同一个副本可能经历多次重开或平行窗口（Fork Run）：

```
[副本：青木疗养院]
  ├─ 窗口 A (Run-01 · 潜入) ── 已结算 ── [候选记忆池] ── (当前非正史，记忆休眠)
  ├─ 窗口 B (Run-02 · 强攻) ── 已结算 ── [候选记忆池] ── ★ 指定为正史 ★ ──→ [正式生效记忆]
  └─ 窗口 C (Run-03 · 探索) ── 进行中 ── [完全隔离] ──── (不可见)
```

### 1. 状态流转三段式
- **`active` 进行中**：记忆绝对隔离，严禁写入或向外部角色泄露；
- **`settled` 已结算 / `abandoned` 已放弃**：触发记忆自动提取，进入**「候选记忆（Candidate）」**；
- **`canonical` 正史指针指定**：
  - 用户在副本管理中将某个 Run 标记为正史（`canonicalRunId = runId`）；
  - **只有正史线中的事件记忆才正式生效**并参与后续推演和角色联络；
  - 若用户后期切换正史到另一条线，**旧线记忆自动退回休眠候选态，新线记忆立即激活生效**；记忆本体无需拷贝，纯指针切换。

## 四、角色在场与记忆可见性法则

在剧情推演与联络模块中，记忆不是全知广播，遵循严格的信息茧房法则：

1. **高危角色与队友限制**：
   - 只有在事件发生时**处于在场列表（`witnesses`）中**的角色，才能够“回想起”该段记忆；
   - 未在场的角色即使处于正史线，也绝对不会无端获知该事件，确保角色逻辑自洽。
2. **系统助手特权**：
   - 「系统助手」（System Assistant）拥有因果视界最高权限，**无条件可见正史线中的所有事件记忆**，可随时调取辅助执行员。

## 五、自动提取管线规范 (Auto Extraction Pipeline)

在副本结算（或放弃）完成时，向 API 发起一次后台静默记忆总结请求：

```
[推演对话记录 Records] 
         │
         ▼
[API 提炼请求 (Prompt 约束)] 
  - 要求客观精简，避免主观抒情
  - 提取 5~6 个核心关键词
  - 识别在场高危角色与队友
         │
         ▼
[输出结构化 JSON 数组] ──→ 写入 mem/doc.{runId} ──→ 等待正史指派
```

## 六、数据归档 (02 MEMORY BANK) UI 规范

### 1. 布局体系
- **顶部 Header**：
  - 标题 `MEMORY BANK // 数据归档`
  - 返回桌面按钮（遵循 iOS 灵动岛保护 Safe Area）
  - 全局搜索栏（支持关键词快搜与全文检索）
- **左侧 / 顶部分类导轨**：
  - 全部记忆（ALL ARCHIVE）
  - 按副本划分战术标签（筛选指定副本下的事件库）
  - 正史筛选胶囊（全部 / 仅正史 / 候选）
- **事件卡片流 (Memory Bento Card)**：
  - 外壳圆角 `4px`，深墨毛玻璃底板 + 1px 暗金/细边微光；
  - 顶部：副本代号与名称 + 窗口分支标识 + `正史 CANONICAL`（暗金）/ `候选 CANDIDATE`（灰褐）状态徽章；
  - 正文：精简客观事件描述；
  - 底部左侧：5~6 枚纯文字关键词胶囊；
  - 底部右侧：在场见证者角色微标（纯文字胶囊或高危角色头像）。

### 2. 工地施工协议坚守
- **严禁使用 Emoji**，状态徽章与分类图标 100% 纯矢量 SVG；
- **严禁物理分割线**，通过背景色块层级与间隙区分模块；
- **全屏灵动岛保护**。
