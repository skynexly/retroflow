> **版本**：v1.0.0

## 1. 系统定位与核心原则

记忆库是快穿/无限流战术终端的核心叙事与上下文沉淀中枢。  
在多分支并行、多周目重开的机制下，记忆必须解决**“因果污染”**与**“跨线记忆错乱”**的问题。

### 1.1 双维度解耦
- **事件记忆（Event Memory）**：
  - 以**副本 Run / 分支窗口**为沉淀单位。
  - 记录“在这个世界里发生过什么客观事实、关键抉择与关键因果”。
  - 具有严格的**正史生效周期**与**分支隔离**机制。
- **角色记忆（Character Memory）**：
  - 以**高危角色 / 核心 NPC**为沉淀单位。
  - 记录性格偏好、好感羁绊、对执行员的主观认知、历史微表情与心理防线。
  - 架构更复杂，当前阶段暂挂起，后续独立扩展。
- **跨维度交汇点**：
  - 事件记忆记录 `在场角色（witnesses）`。
  - 角色只能检索到**自己作为 witness 在场**、或在设定上有渠道知晓的事件记忆；
  - **系统助手（System Assistant）**拥有全知监察权限，无条件命中所有正史记忆。

## 2. 事件记忆状态机与正史指针

### 2.1 三段式生命周期
```
[ 副本运行中 active ]
      │ (记忆严格隔离在当前 run，不向外广播)
      ▼ 副本通关结算 (settled) / 执行员主动放弃 (abandoned)
[ 候选记忆池 candidate ]
      │ (进入待命区，记录完整因果，但对外界不可见/未生效)
      ▼ 用户/系统指定为正史 (canonicalRunId)
[ 正史生效 active canonical ]
      │ (所有通用模块、后续副本、角色检索正式引用)
      ▼ 若用户切换正史指针到另一条结算线
[ 退回候选 candidate ] (引用无缝热切换，无需物理重写数据)
```

### 2.2 正史与候选的设计保障
1. **单一正史原则**：同一个 `forkId`（同类副本或同一起点分支组）下，同一时刻只认一条 `canonicalRunId`。
2. **零破坏热切换**：
   - 切换正史只需改变副本索引中的 `canonicalRunId` 指针。
   - 检索记忆时，过滤条件为：`memory.runId === fork.canonicalRunId && (memory.status === 'settled' || memory.status === 'abandoned')`。
   - 换线时记忆瞬间无感知对齐新线，老线记忆保留在候选池中，随时可换回。

## 3. 事件记忆数据结构（Event Memory Schema）

```json
{
  "id": "mem-ev-20261012-001",
  "forkId": "fork-ark-01",
  "forkTitle": "方舟降临：第七回响",
  "runId": "run-20261012-a8f3",
  "runSeq": 3,
  "status": "settled",
  "isCanonical": true,
  "createdAt": 1791823900000,
  "updatedAt": 1791824100000,
  
  "summary": "执行员在核心控制区拒绝交出黑匣子，强行启动备用冷却回路，导致主控系统发生局部过载，但成功保全了地下避难所供氧。",
  
  "keywords": [
    "黑匣子",
    "核心控制区",
    "冷却回路",
    "系统过载",
    "避难所供氧",
    "抉择"
  ],
  
  "witnesses": [
    {
      "charId": "char-eva",
      "charName": "伊娃",
      "threatLevel": "CRITICAL"
    },
    {
      "charId": "char-chen",
      "charName": "陈队长",
      "threatLevel": "HIGH"
    }
  ],
  
  "importance": 4,
  "tags": ["核心抉择", "设施破坏", "生还"]
}
```

### 3.1 核心字段说明
1. **`summary`（具体事件）**：
   - 100~150 字内的客观精炼叙事，禁止废话与内心独白。
   - 必须包含**“因（起因/选择）”**与**“果（后果/世界状态变化）”**。
2. **`keywords`（事件关键词）**：
   - 严格限定在 **5 ~ 6 个**。
   - 覆盖核心道具、场景地点、关键动作、因果实体，用于后续 RAG 向量/BM25 混合检索与高频标签聚合。
3. **`witnesses`（在场角色）**：
   - 仅记录在场的高危/重要角色名单。
   - 角色检索逻辑：角色 A 只能回忆 `witnesses.includes(A)` 的正史事件。
   - 系统助手逻辑：无条件命中，忽略 `witnesses` 限制。
4. **`importance`（权重等级）**：
   - 1~5 级战术重要度，用于上下文窗口预算紧缩时的动态截断。

## 3.5 存储层设计（独立 `memories` store）

### 3.5.1 存储选型决策
- **严禁 localStorage**：记忆是只增不减的流水，5MB 硬上限必爆，且同步读写会卡 UI；
- **不复用 `records` 流水库**：记忆需要按关键词、按在场角色做高频反查，`records` 的通用索引粒度不够，量大后只能全捞内存过滤；
- **独立 object store**：`DB_VERSION` 2 → 3，新建 `memories` store（`keyPath: 'id'`），索引一次升到位，老用户 `onupgradeneeded` 无感升级。

### 3.5.2 事件记忆与角色记忆同库不同型
两类记忆共用一个 `memories` store，以 `memKind` 字段判别（`'event'` / `'char'`）。
理由：两者交集（在场角色、来源副本、关联事件）需要跨类型引用，同库查询与事务都方便。

**事件记忆（本阶段实施）**：
```
{ id, memKind:'event', forkId, forkTitle, runId, runSeq, status, isCanonical,
  summary, keywords[5~6], witnessIds[], importance, tags[], createdAt, updatedAt }
```

**角色记忆（预留 schema，本阶段不做 UI）**：
```
{ id, memKind:'char', charId, summary, keywords[],
  sourceForkId, sourceRunId,      // 来源副本（交集点①）
  linkedEventIds[],                // 关联的事件记忆（交集点②）
  status, createdAt }
```

### 3.5.3 `witnesses` 扁平化为 `witnessIds`
在场角色从对象数组改为**纯 ID 数组**（multiEntry 索引要求扁平数组才能按角色反查）。
角色名字、威胁等级展示时从角色档案库（roster 域）现取——角色数据是权威源，
记忆里不冗余快照，角色改名也能全局同步。

### 3.5.4 索引表
| 索引名 | 键路径 | multiEntry | 用途 |
| --- | --- | --- | --- |
| `by_kind_time` | `[memKind, createdAt]` | 否 | 分类型时间线分页 |
| `by_fork_run` | `[forkId, runId]` | 否 | 正史/候选主查询路径 |
| `by_status` | `status` | 否 | 候选池筛选 |
| `by_keywords` | `keywords` | **是** | 5~6 关键词各自可命中，反查零扫描 |
| `by_witness` | `witnessIds` | **是** | 角色回想在场事件的直接通道 |
| `by_char_time` | `[charId, createdAt]` | 否 | 角色记忆主查询（先备索引，暂不写入） |

### 3.5.5 配套
- `DataRegistry` 新增 **`memory` 域**（`memory/` 前缀）：docs 侧放记忆库元配置（提取开关、预算参数），"清存储"面板天然可见记忆域占用；
- `js/memory-store.js`：记忆库专属存取模块（候选写入、正史/候选过滤、关键词/角色检索、假数据播种），业务代码统一走它，不直接摸 IndexedDB；
- `data-vault.js` 后续追加 `memory` 导出块，记忆可随全量备份走。

## 4. 自动提取与 API 整理规范（规划）

后续接入 AI 自动整理时，在副本结算或节点触发后发起专用单次 Prompt：
- **Prompt 重点**：
  1. 梳理不可逆的世界状态改变；
  2. 提取最具有因果蝴蝶效应的行为；
  3. 识别现场直接目击或有通讯感知的关键人物（高危角色）；
  4. 产出恰好 5~6 个关键词与结构化因果段落。

## 5. 桌面 02「数据归档 MEMORY BANK // 记忆库」UI 规划

### 5.1 页面形态与战术美学
- **容器与手势**：
  - 遵循系统标准全屏 App 容器（如 `.memory-app`），支持顶部手势滑条与 iOS 灵动岛保护（`padding-top: max(env(safe-area-inset-top), ...)`）；
  - 顶栏双区域：左侧战术返回键（SVG 纯矢量）、主副标题（`02 // MEMORY BANK`、`数据归档 // 记忆库`）；右侧战术操作区（搜索开关、筛选器、正史线指示）。
- **视口与层级**：
  - **模块 A：顶部统计与正史视窗**：
    - 当前正史归档总数、各副本已收录事件计数；
    - “正史记忆”与“候选池（候补分支）”双切换 Tab。
  - **模块 B：快速检索与关键词云**：
    - 5~6 关键词构成的紧凑战术胶囊组，点击即过滤；
    - 搜索输入框（纯矢量放大镜 SVG）。
  - **模块 C：事件记忆战术卡片流（Card Stream）**：
    - 每张卡片呈现：
      - 副本编号 + 章节标签 + 正史微标（金/绿）；
      - 核心事件因果正文（高对比可读字号）；
      - 5~6 枚关键词轻微标；
      - 在场角色小头像/名牌胶囊（仅高危角色）；
      - 发生时间 / 结算周目代号（如 `RUN-03 #CANONICAL`）。
- **严苛规范约束**：
  - 🚫 严禁任何 Emoji（全部采用纯矢量 SVG 图标）；
  - 🚫 严禁任何物理分割线（纯靠 `margin`、`gap`、卡片微透底衬与边框区隔）；
  - 适配 iOS 灵动岛与底部安全区（Safe Area Insets）。
